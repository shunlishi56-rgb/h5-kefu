H5 在线客服系统 · 运维排查手册

进程 / 端口 / 保活 / 数据 / 会话机制 —— 从「服务挂了」到「自己搞定」

适用说明：本手册适用于已部署的 H5 在线客服系统（Node.js 版）。文中命令默认约定：项目目录 /www/wwwroot/h5-kefu-v2、服务端口 3000。若你的实际目录或端口不同，把命令中对应的部分替换即可。所有命令均在服务器的 SSH 终端（宝塔终端 / Xshell）中执行，可直接整段复制粘贴。

一、30 秒快速自检

遇到任何异常，先跑这三板斧，90% 的问题在 30 秒内就能定位方向：进程活没活、端口通没通、页面开不开。

  1. 第一板斧：看进程

    检查 node server.js 进程还在不在，顺便看它的启动时间和已存活时长。

  2. 第二板斧：看端口

    检查 3000 端口有没有进程在监听，以及是「谁」在监听。

  3. 第三板斧：看页面

    浏览器访问 http://你的服务器IP:3000/admin ，看客服后台能不能打开。

# 第一板斧 + 第二板斧，两条命令直接复制执行
ps -eo pid,lstart,etime,args | grep "node server.js" | grep -v grep
ss -tlnp | grep 3000

对照下表定位问题：

进程3000 端口结论怎么办
有有服务正常，问题在访问链路上浏览器按 Ctrl+F5 强制刷新；仍打不开则是端口没放行，去云服务商控制台和宝塔面板放行 3000
有没有进程活着但没监听 3000 —— 多半是跑在了错误端口（旧端口残留进程）见第三章 3.5「多余进程清理」
没有没有服务彻底挂了看第三章 3.1 判断怎么挂的，再按第四章流程重启
有多个有双进程并存，其中一个是多余的见第三章 3.5「多余进程清理」

二、症状速查表：按现象找原因

先对号入座，再按指引的章节处理。

现象大概率原因处理办法
页面一直转圈打不开（超时）3000 端口没放行。注意要放行两个地方：云服务商控制台的「安全组」+ 宝塔面板的「安全」两处都放行后，浏览器 Ctrl+F5 强刷再试
页面能打开，但消息发不出去 / 收不到WebSocket 连接断开，或服务进程异常先 Ctrl+F5 强刷；无效则按第一章自检进程，见第三章
浏览器控制台报 Unexpected token '<'接口返回了 HTML 错误页 —— 服务没跑起来，或依赖残缺先按第一章自检；服务在跑则按第四章重装依赖
浏览器报 Failed to fetch访问地址写错：比如用了 127.0.0.1 或漏了 http:// 前缀改用服务器公网 IP，地址必须以 http:// 开头
页面报 500 错误数据文件损坏或读写冲突按第五章数据部分：停服务再启动，一般即可恢复
启动时报 EADDRINUSE（address already in use）3000 端口已被其他进程占用见第三章 3.5，查出占端口的进程并处理
换电脑 / 手机后聊天记录全没了不是故障 —— 会话机制认浏览器不认人见第五章「会话识别机制」

三、进程与保活排查（核心）

3.1 判断进程断没断过

看进程的「出生时间」就能判断：如果启动时间就是你部署那天的时间，说明从部署起就没断过；如果启动时间是最近的（几分钟前、几小时前），说明中途断过、被保活任务自动拉起来了 —— 断几次，就有几个「较新」的启动时间可查。

# pid 进程号 | lstart 启动时间 | etime 已存活时长
ps -eo pid,lstart,etime,args | grep "node server.js" | grep -v grep

输出示例（时间就是线索）：

  PID  STARTED          ELAPSED   COMMAND
26344  Sun Sep 27 12:12  1-03:20:42  node server.js
# 启动时间 = 9月27日 12:12，已连续存活 1天3小时 → 期间没断过

3.2 查有没有被系统「悄悄杀掉」（内存不足）

服务器内存不够时，系统会直接杀掉最占内存的进程，而且不会有任何界面提示。这是「进程莫名其妙消失」的头号原因。

dmesg -T | grep -i -E "oom|kill" | tail -20

如果看到 Out of memory: Killed process 字样，说明进程是被系统因内存不足杀掉的，解决办法：升级服务器配置，或增加 swap 交换空间。

3.3 查服务器自己重启过没

服务器重启后进程自然全没了（有保活的话会自动爬起来）。查一下就知道：

last reboot | head -5

如果输出里有近期的重启记录，说明服务中断是服务器重启导致的，不是程序的问题。

3.4 看运行日志

服务运行的全部输出都记录在项目目录下的 run.log 里，报错信息第一时间看这里。

tail -30 run.log   # 看最近 30 行
tail -f run.log    # 实时滚动盯着看，Ctrl+C 退出

3.5 多余进程清理（改端口后必查）

正常情况服务器上只应该有一个 node server.js 进程。如果 ps 查出来有多个，通常是因为改过端口部署：旧端口的进程还活着，新端口的进程又被拉起来了，两个并存。多余的进程不仅白占内存，还会和正式服务共写同一份数据目录，有数据错乱风险，必须清理。

判断口诀：谁占着 3000 谁干活，不占 3000 的都是多余的。放心杀 —— 就算万一杀错，保活任务 1 分钟内会自动拉起，不影响线上。

# 1. 列出所有 node server.js 进程，记下每个的 PID
ps -eo pid,lstart,etime,args | grep "node server.js" | grep -v grep

# 2. 看谁占着 3000（这个是在干活的，留着）
ss -tlnp | grep 3000

# 3. 查多余进程在监听什么端口、在哪个目录跑（确认身份再动手）
ss -tlnp | grep 其他PID
ls -l /proc/其他PID/cwd

# 4. 确认它不占 3000 后，杀掉
kill 其他PID

# 5. 验证：进程只剩一个，3000 还在监听
ps -eo pid,etime,args | grep "node server.js" | grep -v grep
ss -tlnp | grep 3000

真实案例：两个进程并存，端口一新一旧

某服务器上同时查到两个进程：11:48 启动的和 12:12 启动的。逐一排查发现：旧进程（11:48）跑在 6789 旧端口上 —— 是改端口部署前留下的残留；新进程（12:12）占着 3000，是保活任务拉起的正式服务。

处理：kill 掉旧端口进程，只留占 3000 的那个。杀完验证端口和聊天页面正常，问题解决。整个过程服务不中断，因为干活的一直是 3000 上那个。

3.6 保活任务自检

先确认保活任务已保存生效：

crontab -l
# 应能看到这一行（目录、端口按实际）：
# * * * * * /bin/bash -c 'ss -tln | grep -q ":3000 " || (cd /www/wwwroot/h5-kefu-v2 && PORT=3000 nohup node server.js > run.log 2>&1 &)'

再做一次极限测试，验证它真的会自动拉起：

pkill -f "node server.js"
sleep 60
ss -tlnp | grep 3000   # 有输出 = 保活正常，60秒内自己爬起来了

注意：pkill 会断掉正在进行的聊天连接，极限测试请在没有客户在线的时段做。

四、依赖与安装问题

4.1 npm install 报错：E404 / 源配错

安装依赖时报 E404，多半是 npm 的下载源被配错成了无效地址（比如曾被设置成 cdn.npmmirror.com 开头的二进制地址，而不是正规的 registry 地址）。查一下当前用的源，改回官方源或国内镜像源即可：

npm config get registry                # 查看当前源
npm config set registry https://registry.npmjs.org   # 改回官方源
# 国内服务器慢的话用国内镜像：npm config set registry https://registry.npmmirror.com

4.2 依赖残缺的「怪症状」

有一种很迷惑的故障：进程明明跑起来了、端口也在监听，但客服端一登录就报错，浏览器控制台报 Unexpected token '<'，run.log 里出现 Cannot find module 'xxx' 类字样。

这不是代码 bug，是 node_modules 安装中断过、文件不完整导致的。表现就是：服务起得来，接口全废（返回的是 HTML 错误页而不是数据）。

4.3 标准重装流程（一次搞定）

# 1. 停掉现有进程
pkill -f "node server.js"

# 2. 进入项目目录
cd /www/wwwroot/h5-kefu-v2

# 3. 删干净残缺的依赖，重装
rm -rf node_modules
npm install

# 4. 重新启动
PORT=3000 nohup node server.js > run.log 2>&1 &
disown -h %1

看到 npm install 结尾出现 added xx packages 且没有 vulnerabilities 以外的红色报错，就算装好了。

五、数据与会话机制（客服方常问）

5.1 系统怎么认出「同一个客户」？

Q: 是根据 IP 或设备判断的吗？客户换地方还认得出来吗？

A: 都不是。系统是在访客浏览器的本地存储（localStorage）里存一个随机 ID：客户第一次打开聊天页时自动生成，之后每次打开自动读取。服务端按「客服 ID + 访客 ID」绑定同一个会话。所以同一浏览器打开同一客服的链接，永远接着同一个会话聊，历史记录完整保留。

场景结果
同一手机 / 浏览器反复打开聊天页同一客户，会话延续，记录完整
换手机、换电脑打开新客户（新设备上没有那个 ID）
清了浏览器缓存 / 微信清理了缓存新客户（ID 被清掉）
无痕 / 隐私模式打开新客户（关闭即丢失）
换了另一个客服的聊天链接同一访客，但在新客服名下开新会话

给客服的解释话术：这是免登录系统的通用设计 —— 零门槛（客户不用注册），代价是「认浏览器不认人」。客户反馈「记录没了」，先问一句是否换了设备或清理过缓存。

5.2 数据存在哪、怎么备份

目录内容
data/客服账号 + 全部聊天记录（按会话逐文件落盘，无需数据库）
uploads/聊天中收发的图片文件
 
# 备份（在服务器上执行，生成压缩包在 /www 下）
cd /www && tar czf kefu-backup-$(date +%Y%m%d).tar.gz h5-kefu-v2/data h5-kefu-v2/uploads

迁移到新服务器：把整个项目目录拷贝过去，执行一次 npm install 再启动即完成，聊天记录原样带走。

重要：页面突然集体报 500，多半是数据文件读写冲突 —— 先停服务再重新启动，一般即可恢复。手工替换或修改 data/ 里的文件前，必须先停掉服务进程，带服务运行时改数据文件容易写坏。

附录：两个常见「为什么」

深挖：为什么我明明用了 nohup 启动，关掉 SSH 窗口服务还是挂了？

部分服务器环境下，单独的 nohup 不够保险：SSH 会话结束时子进程仍可能被一并带走，表现就是「终端一关，服务就没了」。

两个办法，建议都配上：

  • 当下启动用 disown：执行启动命令后，紧接着输入 disown -h %1，之后用 exit 命令正常退出 SSH（不要直接点 X 关窗口）。
  • 长期兜底用 crontab 保活：每分钟自动检查端口，进程没了就自动拉起。就算服务器重启、进程意外崩溃，最多 1 分钟自动恢复。这是根治方案，配置方法见部署文档。
深挖：想换一个端口跑，要改哪些地方？

换端口有四处要同步改，漏一处就出「端口对不上」的怪问题：

  • 启动命令里的 PORT=3000 改成新端口；
  • 保活 crontab 那一行里的两处端口（检测的端口 + 启动的端口）同步改；
  • 云服务商安全组和宝塔面板放行新端口；
  • 已经发出去的聊天链接地址全部更新，旧端口的残留进程记得按 3.5 节清理。

排查心法

三步走：先自检（第一章 30 秒定位方向）→ 按症状找原因（第二章速查表）→ 按章节深挖处理（第三至五章）。

90% 的故障逃不过三样：进程挂了、端口没放行、依赖残缺。

交付前三件事：改掉初始密码 admin123 ｜ 配好 crontab 保活 ｜ 放行端口并验证页面可访问。
